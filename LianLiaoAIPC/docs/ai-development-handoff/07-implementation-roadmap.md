# 完整开发路线图

## 1. 执行方式

本路线按依赖和风险排列，不等同于一次性大改。开发 AI 应逐阶段交付：

1. 只读盘点当前代码、工作区和真实数据来源；
2. 为阶段产出或更新专项设计与实施计划；
3. 按测试驱动完成纵向切片；
4. 执行阶段验收；
5. 使用 Conventional Commit 格式和中文主题提交相关文件；
6. 更新 [03-current-status.md](./03-current-status.md) 后再进入下一阶段。

每个阶段都可以包含三个仓库，但不得在缺少需要时修改 `cloud-service` 或 `vip_store`。不自动执行数据库写脚本，不自动推送远端。

## 3. 阶段 0：稳定开发基线

### 目标

确保后续 AI 不覆盖用户改动，也不在错误环境上继续开发。

### 任务

- 检查 `AI_lianliao` 与 `lianshang_liaoning` 的工作区状态和近期提交；
- 核对当前未提交 `app-mark.png`、侧栏样式和 DOM 测试差异；
- 运行相关企业侧栏/退出测试，确认品牌修改是否完整；
- 验证 Electron 本地基地址为 `127.0.0.1:12580`，本地请求不回退生产；
- 验证开发 F12 与生产 DevTools 边界；
- 验证 bundled AionCore 解析测试；
- 记录基线测试结果和已存在但与本任务无关的失败。

### 完成条件

- 未提交用户改动被明确保留或按用户指示单独提交；
- 后续阶段有干净、可解释的变更范围；
- Electron、gateway、cloud-api、H5 的本地联调拓扑已确认。

## 4. 阶段 1：Electron 普通用户在线咨询

状态：**代码已完成，待真实环境验收**（2026-07-20）。

权威规格：

[2026-07-20-electron-customer-consultation-design.md](../superpowers/specs/2026-07-20-electron-customer-consultation-design.md)

### 目标

普通企业用户可在 Electron 咨询真人客服；`roleId=19` 客服账号只看到“客服接待”，其他账号只看到“在线咨询”。H5 客服可以接待并回复 Electron 客户。

### 实现切片

1. **公共契约**：补齐客户会话、客户消息和连接状态的 Renderer DTO 与 Zod schema；复用现有客服有符号字符串 ID。
2. **主进程客户 Gateway**：基于当前企业会话的 `openId` 调用 `/customer/auth`，令牌只保留在主进程；实现鉴权、打开会话、历史、已读、关闭、上传、ticket 与 WebSocket。
3. **Preload/IPC**：增加客户侧最小调用和事件订阅，校验 sender；不得复用通用网络入口。
4. **客户状态机**：连接、历史、ack、重连补拉、幂等、未读和结束状态；与客服接待状态隔离。
5. **页面**：新增 `/enterprise/consultation`，提供消息列表、文本/图片输入、连接反馈、历史加载与结束会话。
6. **互斥导航**：`roleId=19` 只显示 `/enterprise/customer-service`；其他用户只显示 `/enterprise/consultation`。导航和路由守卫都要覆盖。
7. **桌面提醒**：普通用户在非咨询页或窗口不聚焦时收到客服回复通知；点击定位会话；托盘未读与现有客服接待未读互不串台。
8. **退出清理**：退出企业会话时断开客户连接并清除客户令牌、ticket、未读和通知状态。

### 推荐测试

- 客户 schema/ID 边界；
- 客户 Gateway 鉴权、白名单、令牌不泄露、重连；
- IPC sender 与事件反注册；
- 普通用户/客服互斥菜单和直接路由守卫；
- 消息发送、图片、失败重试、结束、通知定位；
- 退出登录资源清理。

### 完成条件

真实链路通过：

```text
Electron 普通账号发消息
→ cloud-api 持久化与 WebSocket
→ H5 roleId=19 客服收到并回复
→ Electron 实时收到回复和系统通知
```

原则上本阶段不需要后端或 H5 新功能；发现契约缺陷时才做最小修复。

### 当前实施结果

- 公共契约、固定 API Client、客户 Gateway、IPC、Preload 与 Renderer Client 已完成；
- 客户端单会话状态机、文本/图片、历史、已读、结束、重试与滚动体验已完成；
- `roleId=19` 与普通账号的菜单和路由互斥已完成；
- 客户未读、系统通知、托盘显示和点击固定导航已完成；
- 聚焦自动化已覆盖协议、Gateway、IPC、状态机、页面、路由和通知；
- 未修改后端、H5 和数据库。

剩余工作只包括真实环境联调、Windows 客户端通知/托盘人工验证和发布门禁，不应再重复实现第二套客户会话能力。

## 5. 阶段 2：收藏与商机跟进

### 2A. 我的收藏

#### 只读调查

- 核对 `J_CY_INTEREST` 列、逻辑删除/状态、创建时间和用户关联字段；
- 核对 H5 企业/产品/项目收藏的请求与取消逻辑；
- 检查重复有效记录与现有索引；
- 查明供需对象的收藏类型，但本切片先只做企业 `1`、产品 `2`、项目 `6`。

#### 实现

- cloud-api 提供收藏状态、保存、取消、分页列表稳定契约；
- 写操作使用可信桌面身份并保持幂等；
- 企业、产品、项目列表/详情增加统一收藏按钮；
- 实现 `/enterprise/favorites` 正式页面，支持类型筛选、分页和跳转详情；
- 首页收藏指标改为真实聚合数据。

#### 数据库边界

如需清理重复数据、增加唯一约束或新索引，先输出只读统计、SQL 草案、锁影响和回滚方案，等待用户确认。

### 2B. 商机跟进

#### 只读调查

- 核对 `J_OPP_LEAD`、项目外部 `hpInfoId`、用户/企业关系和状态字段；
- 查明同一企业、用户、项目的唯一语义；
- 确认状态是否可跳级、回退或恢复。

#### 实现

- 统一桌面查询/创建/推进商机契约；
- 在项目详情中显示跟进状态与下一步操作；
- 实现 `/enterprise/leads`：搜索、状态筛选、分页、更新时间线；
- 收藏与商机保持独立，二者可以同时存在；
- 首页商机指标使用真实数据。

### 完成条件

- 收藏重复点击不产生重复有效记录；
- 列表、详情和“我的收藏”状态一致；
- 商机状态有明确服务端校验和审计时间；
- 翻页自动滚动到表头，loading/空态占满列表宽度。

## 6. 阶段 3：项目权益与联系方式解锁

### 调查问题

- 哪个会员权益代码允许解锁项目联系人；
- 免费次数、付费次数、有效期和企业/个人归属；
- H5 现有解锁接口是否具备服务端可信身份、事务和幂等；
- 解锁记录和联系方式的权威表；
- 并发点击、失败补偿和退款语义。

### 实现

- 后端提供“查询解锁资格/剩余次数”和“确认解锁”稳定接口；
- 使用幂等键在单事务内校验权益、扣减、写记录；
- Electron 项目详情展示真实权益说明、确认弹窗和成功刷新；
- 已解锁用户可查看真实联系方式，未解锁继续保持隐私；
- 将解锁成功的项目加入或关联商机跟进，但不能自动伪造跟进状态。

### 完成条件

- 同一请求重试不重复扣减；
- 权益不足、过期、网络失败、并发冲突均有明确反馈；
- 未授权接口不能返回联系方式。

## 7. 阶段 4：供需对接

此阶段数据来源尚未确认，必须先输出“供需模型调查报告”并让用户确认。报告至少回答：

- 权威供给/需求表、主键和发布主体；
- 类型、状态、行业、地区、有效期、联系方式和附件字段；
- 当前 H5 入口、Controller/Service/Mapper 和旧接口；
- 审核、上架、下架、过期和删除规则；
- 收藏类型、询价/留言/对接记录的真实表；
- 哪些联系方式受会员或积分限制。

确认后分切片开发：

1. 供需大厅列表、筛选、分页、详情；
2. 企业/产品/项目上下文推荐；
3. 收藏、询价或发起对接；
4. 我的对接记录与状态；
5. 供需发布、编辑、审核状态与下架；
6. 首页供需指标和 ECharts 趋势。

验收必须使用真实供需记录，不以 mock 列表代替服务端能力。

## 8. 阶段 5：会员、积分、收费与企业数据发布

### 5A. 会员账户

调查并确认正式会员等级、套餐、价格、有效期、权益代码、发布额度和项目解锁次数。随后开发：

- 会员总览、当前等级、有效期和权益清单；
- 套餐对比和升级入口；
- 权益消费记录；
- 会员状态与企业码展示保持同一来源。

### 5B. 积分

先确认权威余额与账本，不自行用汇总字段替代账本。开发：

- 可用、冻结、将过期积分；
- 获取/消费明细和分页；
- 业务扣减幂等、事务、审计和补偿；
- 任何页面不能只在前端修改余额。

### 5C. 收费与订单

必须由用户确认支付渠道、金额来源、订单状态机、回调签名、退款和发票边界。开发：

- 服务端创建订单并冻结服务端价格；
- 支付二维码/跳转和轮询；
- 可信回调、幂等入账和订单详情；
- 失败、关闭、超时、退款状态；
- Electron 只展示服务端订单事实。

### 5D. 企业数据发布

按企业、产品、供需分别确认权限与审核流，开发：

- 草稿、新增、编辑、预览、提交审核；
- 审核中、已通过、已驳回、已下架；
- 驳回原因、再次提交、发布额度；
- 我的发布列表和操作记录；
- cloud-api 强制校验企业归属和操作权限。

### 完成条件

- 会员、积分、订单、发布四个领域有各自清晰状态机；
- 价格、余额、权益和发布权限全部以服务端为准；
- 支付和数据库写脚本已获得用户专项确认并完成沙箱/测试环境验收。

## 9. 阶段 6：企业 AI 助手

### 目标

让链辽AI使用当前登录企业的授权业务数据辅助检索、总结和生成操作草稿，但不自动执行高风险操作。

### 实现

- 建立企业 AI 上下文白名单：企业基本信息、公开产品、公开项目、收藏、商机和允许的供需数据；
- 在主进程/后端裁剪数据，禁止 Renderer 自行拼接敏感字段；
- 企业 AI 会话与通用 AI 会话分区标识；
- 支持从企业/产品/项目详情携带结构化上下文进入链辽AI；
- AI 可以生成发布草稿、跟进建议和查询条件；
- 收藏、解锁、发布、支付、转接、关闭等写操作必须显示确认卡，并由确定性代码再次校验；
- AI 区域提供明确“返回链上辽宁·产业云城”入口。

### 完成条件

- AI 看不到当前用户无权访问的联系人、客服会话或其他企业私有数据；
- AI 输出不是业务成功事实，真实结果来自 API；
- 所有结构化动作有审计、确认和失败反馈。

## 10. 阶段 7：消息中心与桌面工具中心

### 聚合消息中心

统一展示但不混淆来源：

- 客服未读；
- 供需对接和回复；
- 商机跟进提醒；
- 数据审核结果；
- 会员/积分/订单变化；
- 客户端更新和系统异常。

要求事件有稳定类型、业务对象 ID、已读状态和目标路由。托盘角标与消息中心未读保持一致，点击通知必须安全定位。

### 桌面工具中心

基于已有 Electron 壳能力提供企业化入口：

- 版本号、更新检查、下载进度、重启安装；
- AionCore 状态和受控重启；
- 网络、gateway、cloud-api、WebSocket 诊断；
- 日志目录和隐私脱敏后的诊断导出；
- 通知权限与测试通知；
- 环境信息只读展示。

工具中心不得显示敏感 token、完整 OpenID、数据库凭据或聊天正文。

## 11. 阶段 8：系统验收与发布

- 使用普通账号、新注册账号、无企业账号、`roleId=19` 合格客服、仅 roleId 不合格客服做权限矩阵；
- 使用真实微信扫码、模板消息、H5 跳转和 Electron/H5 双端消息联调；
- 验证 Oracle/Redis/Nacos 重启、WebSocket 断线和网关超时恢复；
- 验证 Windows 安装、首次启动、升级、回滚和卸载；
- 验证 AionCore 随包资源及安全软件误报处理；
- 执行三仓完整测试、类型检查、构建和关键页面视觉检查；
- 生成发布说明、数据库变更说明、配置变更说明和回滚步骤。

## 12. 必须向用户确认的业务问题

开发 AI 先通过源码、H5、Mapper 和只读数据库尽量缩小问题；仍无法确定时一次只提出会改变实现的具体选择：

1. 供需对象、收藏类型和询价/对接状态的权威模型；
2. 商机状态跳转与回退规则；
3. 项目解锁使用的权益、次数和归属；
4. 会员套餐、价格、有效期和发布额度；
5. 积分账本、过期、冻结和扣减规则；
6. 支付渠道、回调、退款与发票范围；
7. 企业/产品/供需的审核角色和流程；
8. 哪些聚合消息需要系统通知或微信提醒。

提问时应附上：已查证的候选实现、源码/表证据、推荐选项、不同选项的影响。不要只问“数据从哪里来”。
