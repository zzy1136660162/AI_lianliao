# 工程开发规范

## 1. 基本原则

1. 以真实源码、测试和已确认契约为依据，不用页面假数据掩盖接口问题。
2. 每次只完成一个可独立验收的纵向切片，避免同时改动三个仓库的大量无关文件。
3. 先调查、再设计、再用测试固定行为、最后实现。
4. 保留用户已有改动；开始和提交前都检查 `git status --short`。
5. 未确定的数据来源、权限、计费或审核规则必须先做只读调查，仍无依据再提出具体问题。

## 2. 测试驱动流程

功能和缺陷统一采用以下循环：

1. 写出能准确表达新行为的失败测试；
2. 运行测试并确认失败原因是“能力尚未实现”，而不是测试本身错误；
3. 编写满足测试的最小实现；
4. 运行聚焦测试、类型检查和相关回归测试；
5. 必要时重构，测试保持通过；
6. 完成阶段门禁后再提交。

不要先写完整实现再补装饰性测试。涉及 Electron IPC、身份令牌、WebSocket 状态机、ID 精度、滚动容器和权限守卫时，必须有自动化覆盖。

## 3. Electron 安全边界

### 3.1 分层职责

| 层       | 允许职责                                           | 禁止职责                                          |
| -------- | -------------------------------------------------- | ------------------------------------------------- |
| Renderer | 展示、表单、本地交互、调用受控 bridge              | 直接访问 Node、文件系统、任意 URL、持有敏感令牌   |
| Preload  | 暴露最小、强类型、白名单 IPC 接口                  | 暴露通用 `ipcRenderer` 或任意网络能力             |
| Main     | 校验输入、受控 HTTP/WS、凭据管理、通知、托盘、更新 | 把令牌/OpenID 回传 Renderer，接受任意 method/path |

新增企业接口时沿用 allowlist operation 模型：Renderer 只提交操作名和经过 schema 校验的参数，主进程把操作映射到固定 method/path。不要增加 `request(url, options)` 形式的通用后门。

### 3.2 身份与会话

- 扫码登录返回的 `openId` 可以明文用于既有兼容接口，但不能作为新增写操作的唯一授权依据。
- 客服短期令牌、WebSocket ticket、用户上下文保存在主进程内存或既有安全存储中。
- Renderer 只能拿到经过裁剪的展示上下文和业务 DTO；为兼容现有企业上下文可以含明文 `openId`，但后端写操作和客服 Gateway 不得信任 Renderer 自选的 `openId`。
- 退出登录时必须清理 HTTP 会话、客服连接、未读数、系统通知状态和缓存。

### 3.3 URL 与外链

- API 目标必须命中受控基地址和路径白名单。
- 外部浏览器跳转使用已有安全 URL 工具，拒绝非 `http/https` 协议。
- 本地与生产环境由统一配置切换，不能在 JSX 中硬编码地址。

## 4. TypeScript 与 React 规范

- 业务代码使用 TypeScript；新增公共数据结构优先使用明确的 `type`/`interface` 和 Zod schema。
- 禁止使用 `any` 绕过外部响应校验；未知响应先作为 `unknown` 解析。
- 业务 ID 使用字符串，格式为非零有符号整数：`^-?(?:[1-9]\d*)$`。
- `userId`、企业 ID、产品 ID、项目 ID、会话 ID、消息 ID 等都不得转换为 JavaScript `number`。
- 异步请求必须覆盖 loading、空态、失败、重试和卸载取消/忽略过期响应。
- 组件以业务职责拆分；页面不直接堆叠网络、状态机、表格和弹窗的全部实现。
- 可复用逻辑放到现有 `shared`、`hooks`、`contracts` 或模块服务层，不复制粘贴。

### 4.1 Ant Design React 与 ECharts

企业工作台统一使用 Ant Design React；不要给 React 项目安装或使用 Element Plus。AionUi `AGENTS.md` 的通用界面默认仍是 Arco，用户对企业工作台的 Ant Design 决策只覆盖 `pages/enterprise` 及其企业公共组件，不应擅自迁移链辽AI其他区域。ECharts 通过公共封装管理初始化、`setOption`、ResizeObserver、主题和销毁。

搜索表单、表格、分页、抽屉、弹窗和反馈状态优先复用已有企业组件：

- 搜索输入和按钮高度、基线与间距统一；
- 翻页后调用统一分页滚动能力，滚动到列表表头而不是页面最顶端；
- 初始 loading/空态容器占满列表可用宽度；
- 图表容器必须有确定高度，并在容器尺寸变化时 resize；
- 表格列中的技术 ID 不作为面向用户的标题或详情文案展示。

### 4.2 CSS 与滚动布局

企业工作台字体：

```css
font-family: 'Microsoft YaHei', '微软雅黑', Arial, sans-serif;
```

当前设计语言：白色/浅色背景、15px 卡片圆角、轻阴影、卡片式侧栏、清晰的深色正文。公共色值、圆角、阴影、间距和字体必须使用企业主题 token/变量，不在各页面重复常量。继续维护现有企业主题文件时保持其公共职责；新建组件级复杂样式遵循 AionUi 的 CSS Module 和目录约束。

Electron 全高布局的关键规则：

- 从窗口根节点到业务滚动区形成完整高度链；
- Flex/Grid 子项按需设置 `min-height: 0`、`min-width: 0`；
- 只允许内容主区承担纵向滚动，避免 body 被内容拉长；
- 长文本使用换行、省略或可展开组件，不能撑破表格/抽屉；
- 左侧菜单、主内容和 AI/客服侧栏分别控制溢出，不互相抢滚动。

## 5. Vue H5 规范

- 延续 `vip_store` 现有 Vue 3、路由、请求封装和移动端组件体系。
- 客服协议、角色判断和状态机复用 `src/page/customer-service` 已有封装，不另建不兼容协议。
- 微信环境、普通移动浏览器和刷新恢复都要覆盖。
- `roleId=19` 的客服账号只显示客服接待；普通用户只显示在线咨询。页面隐藏之外，后端仍须做资格校验。
- 输入栏需处理软键盘、底部安全区、列表自动滚动和历史消息向上加载。
- 上传前校验文件类型和大小；使用后端返回的受控 URL 渲染。

## 6. Java 后端规范

- 兼容 Java 8，不使用高版本语法/API。
- Controller 负责参数和响应；Service 负责业务与事务；Mapper/XML 负责持久化，避免跨层堆逻辑。
- DTO 与数据库实体分离，外部响应不泄露内部凭据、无关字段和技术异常栈。
- 新增写接口必须有明确身份校验、权限校验、幂等策略、事务边界和审计记录。
- 客服资格以后端查询为准：账号应同时匹配 `roleId=19`、`LS_PUBLIC_USER.POST='客服'` 及有效状态。
- 消息发送必须支持 `clientMessageId` 幂等，避免重连重发产生重复记录。
- WebSocket 只用于实时推送；历史、详情、转接、关闭、已读和上传继续走 REST。
- Redis 用于短期令牌、ticket、在线态或事件协调，Oracle 是持久业务事实来源。
- 微信提醒通过既有 `PushMessageServiceImpl` 和 `weixinTemplateService`，模板取 `WEIXIN_TEMPLATE.ID=5`；失败要记日志但不能破坏消息主事务。

## 7. 数据与接口规范

- 先复用 H5 真实接口和字段；不要根据页面文案猜 DTO。
- 所有外部响应在边界层归一化：分页、空值、时间、图片 URL、会员字段和错误状态。
- 业务失败不能只依据 HTTP 状态码；同时按项目统一响应结构判断 `code/success/message/data`。
- 列表与详情字段允许后端缺失时展示“暂未提供”，但不能伪造行业、会员、联系方式或商机。
- 已知收藏表为 `J_CY_INTEREST`；类型映射仅使用已确认值。未知供需类型必须查源码/数据库后再定。
- 会员等级文案和图标以 H5 企业码组件及 [04-data-and-api-contracts.md](./04-data-and-api-contracts.md) 为准。

## 8. 注释与文档规范

注释用于解释“为什么”和不可见约束，尤其是：

- 非零有符号字符串 ID 与精度风险；
- Electron 主进程安全边界；
- 角色与客服资格的双重判断；
- WebSocket 重连、补拉和幂等策略；
- 兼容旧 H5 接口的特殊字段；
- 数据库只读或事务边界。

不要给显而易见的赋值、循环或 JSX 逐行注释。公共 API、复杂 Hook/Service、协议结构和临时兼容逻辑应有简洁注释。AionUi 按仓库 `AGENTS.md` 使用英文代码注释和公共函数 JSDoc；Java/H5 遵循各自现有代码风格。若行为、契约或运行方式改变，同一提交内更新本交接包或对应专项文档。

## 9. 国际化与文案

- AionUi 的通用 AI 区域继续遵循现有 i18n 体系；新增 key 后更新全部要求的 locale 并执行 `npm run i18n:types`。
- 企业工作台当前中文优先，但公共组件不得把可变业务文案写死在样式或数据适配层。
- 对用户展示业务名称，不展示数据库表名、内部 operation、技术 ID 或异常栈。
- 产品称谓固定：企业工作台为“链上辽宁·产业云城”，AI 区域为“链辽AI”。

## 10. Git 规范

- 按用户要求直接在各仓库 `master` 开发，不擅自创建工作树或功能分支。
- 提交使用 Conventional Commit 结构并采用中文主题，例如：`feat(customer-service): 开发企业用户在线咨询`、`docs(handoff): 整理项目AI开发交接包`。
- 每次提交只暂存当前任务文件；使用 `git diff --cached --name-only` 复核。
- 不清理、不还原、不顺手格式化用户的无关改动。
- 禁止 `git reset --hard`、未经确认的 `git checkout --` 和破坏性清理。
- 不自动 push；只有用户明确要求时才拉取/推送，并先处理好本地未提交改动与远端冲突风险。
- 数据库变更脚本与代码分开审阅；未经用户确认不执行脚本。

## 11. 安全红线

- 不提交密码、OpenID 样本、真实手机号、数据库连接、Nacos 密钥、微信密钥或用户聊天内容。
- 不记录完整认证响应和敏感请求体到普通日志。
- 不允许仅靠前端 `roleId` 保护客服接口。
- 不允许 Renderer 获得客服 token/ticket 或通用网络权限。
- 不允许用 `Number`、`parseInt`、`+id` 处理业务 ID。
- 不执行数据库写操作，除非用户看过影响范围并明确确认。
