# 产业检索助手供需查询工具设计

日期：2026-08-10

## 目标

在现有产业检索助手的受控工作流中增加第五个逻辑工具 `DEMAND_SEARCH`，让用户能够用自然语言查询供需对接板块中公开且审核通过的数据，并从助手结果卡片进入现有供需详情页。

本功能覆盖供需列表当前公开的全部需求类型，包括采购需求、生产服务、闲置资源和人才服务等。功能不查询发布草稿，不解锁联系方式，不执行抢单、投递或发布操作。

## 设计原则

- 模型只负责识别意图、生成结构化检索计划和评估候选语义匹配。
- 桌面端只执行注册过的逻辑工具，并继续通过主进程白名单请求访问 cloud-api。
- 所有结果事实均来自现有 `demand.types`、`demand.list` 和 `demand.detail` 业务接口。
- 模型不得生成接口地址、SQL、联系方式或任意 `typeId`。
- 模型排序结果只能引用真实业务接口已经返回的候选 ID。

## 架构变更

### 公共工作流契约

产业实体类型新增 `DEMAND`，工作流工具白名单由四项扩展为五项：

- `COMPANY_SEARCH`
- `PRODUCT_SEARCH`
- `PROJECT_SEARCH`
- `COMPANY_BATCH_GET`
- `DEMAND_SEARCH`

目录过滤条件新增：

- `demandType`：模型输出的需求类型名称或业务分组名称。
- `demandStatus`：只允许 `OPEN`、`CLOSED`、`EXPIRED`。

供需工具同时复用现有 `keyword`、`city` 和 `district` 字段。`DEMAND_SEARCH` 不接受工作流 binding；第一版不增加供需与企业、产品、项目之间的跨资源绑定。

### cloud-api 规划与排序

普通计划和工作流计划提示词都增加 `DEMAND` 目标实体。工作流提示词允许 `DEMAND_SEARCH`，并明确：

- “查、找、看看、有哪些”与“需求、供需、订单、外包、闲置资源、岗位”等查询表达组合时，规划为供需查询。
- “我要采购、我要加工、发布需求、发布供需、找供应商报价”等第一人称办理表达仍属于供需发布，不进入 `DEMAND_SEARCH`。
- 无法区分查询与发布时返回澄清问题。
- 模型只输出需求类型名称与状态枚举，不输出数据库 `typeId`。

服务端对模型输出继续执行长度、枚举、工具白名单、拓扑和目标实体校验。供需候选只包含公开摘要字段，排序结果必须是候选 ID 子集。

### 桌面端供需适配器

新增供需目录适配器，并注册到现有适配器表。执行步骤为：

1. 接收经过校验的 `DEMAND` 检索计划。
2. 当计划包含 `demandType` 时调用 `demand.types`。
3. 对类型名称进行去空白、统一大小写和唯一匹配；只有唯一匹配时转换成真实 `typeId`。
4. 将 `demandStatus` 映射为现有接口状态：`OPEN=0`、`CLOSED=1`、`EXPIRED=2`。
5. 调用 `demand.list`，最多扫描 5 页，最多收集 100 个候选。
6. 将需求 ID、类型、标题、地区、预算、摘要、公开标签、发布时间和状态转换为排序候选。
7. 使用真实接口记录生成可信结果，禁止用模型文本覆盖业务字段。

如果类型名称没有唯一匹配，适配器不猜测 `typeId`，保留关键词和其他条件继续检索。这样既避免错误过滤，也允许模型使用业务分组词描述需求。

### 意图路由与工作流选择

企业助手意图路由继续区分 `CATALOG_SEARCH`、`DEMAND_PUBLISH` 和 `CLARIFY`。增加供需查询规则后：

- “查找沈阳机械加工需求”进入产业检索。
- “看看近期闲置设备需求”进入产业检索。
- “我要发布机械加工需求”进入供需发布确认。
- “我有一个机械加工需求”如果缺少查询或发布方向，则要求用户澄清。

桌面编排器对明确供需查询调用工作流规划，使 `DEMAND_SEARCH` 成为实际执行的第五个逻辑工具。若滚动部署期间工作流端点不可用，则回退到支持 `DEMAND` 的单资源 `plan → adapter → rank` 流程。

### 结果展示与会话上下文

可信结果联合类型新增供需结果。供需卡片展示：

- 需求标题
- 需求类型
- 城市与区县
- 预算
- 公开标签
- 发布时间或状态
- 不超过 120 字的匹配原因

查看详情跳转到现有路由：

`/enterprise/supply-demand/:typeId/:demandId`

当前结果范围、换一批排除 ID 和最近会话摘要继续沿用现有内存上下文机制。供需结果的 scope digest 仅保留公开摘要字段。

## 数据流

1. 用户提交自然语言需求。
2. 意图路由判断为产业数据查询。
3. 模型返回以 `DEMAND_SEARCH` 为工具的严格 JSON 计划。
4. cloud-api 和桌面端分别校验工具、字段、状态和拓扑。
5. 供需适配器解析动态需求类型并调用现有公开列表接口。
6. 模型只对真实候选 ID 输出匹配层级与简短原因。
7. 桌面端按语义层级、发布时间、完整度和稳定 ID 排序。
8. 用户点击卡片进入现有供需详情页。

## 失败与降级

- 模型规划失败：明确供需查询可回退到单资源规划；无法安全确定实体时显示现有规划失败提示。
- `demand.types` 失败：不使用类型 ID，继续以关键词、地区和状态查询。
- 类型名称不唯一：不猜测类型 ID，继续宽泛查询。
- `demand.list` 首次请求失败且没有候选：显示目录服务暂不可用。
- 后续分页失败但已有候选：停止继续翻页并进入排序。
- 模型排序失败或返回非法 ID：使用真实候选和固定兜底原因。
- 无候选：显示现有无结果提示及放宽条件建议。
- 联系方式、草稿、抢单、投递和发布能力不作为该工具的降级目标。

## 安全边界

- 不新增数据库写入。
- 不新增模型可控 URL 或任意 HTTP 请求。
- 不向模型传递 openId、userId、companyId、联系电话或联系人。
- `DEMAND_SEARCH` 只能映射到既有 `demand.types` 和 `demand.list` 操作。
- 详情访问继续由现有 `demand.detail` 契约校验需求 ID 和类型 ID。
- 联系方式仍由独立的会员权限和联系方式接口控制。

## 测试策略

按用户要求先开发后测试，不采用 TDD。完成实现后执行风险测试和功能完整测试。

### cloud-api

- 提示词包含 `DEMAND`、`DEMAND_SEARCH`、状态枚举及查询/发布边界。
- 服务端接受合法供需计划并拒绝未知工具、非法状态、非法 binding 和错误最终实体。
- 候选数量、字段长度、需求 ID 和候选 ID 子集校验保持有效。
- 企业助手正确区分供需查询、供需发布和需要澄清的表达。

### 桌面端

- Zod 契约接受合法 `DEMAND_SEARCH`，拒绝额外字段和非法拓扑。
- 供需适配器正确解析唯一类型、未知类型和歧义类型。
- 状态枚举正确映射为 0、1、2。
- 编排器按顺序调用 `demand.types`、`demand.list`、`workflowRank`。
- 分页、100 候选上限、换一批排除和当前结果内筛选有效。
- 排序失败时只展示真实候选。
- 供需卡片字段和详情路由编码正确。
- 发送给模型的候选中不存在联系方式或身份字段。

### 验证命令

- 桌面端受影响单元测试。
- 桌面端 TypeScript 类型检查。
- 桌面端 i18n 类型和完整性检查。
- cloud-api 目录助手与企业意图路由单元测试。
- cloud-api 模块编译验证。

## 完成标准

- 用户可通过产业检索助手查询全部公开供需类型。
- 助手真实执行第五个逻辑工具 `DEMAND_SEARCH`。
- 查询表达不会误跳供需发布，发布表达不会误执行数据查询。
- 结果只来自现有可信业务接口，卡片可进入正确详情页。
- 模型输出非法、排序失败、类型不可解析和分页异常均有安全降级。
- 联系方式、草稿和写操作不进入新增能力范围。
